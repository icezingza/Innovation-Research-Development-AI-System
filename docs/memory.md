# 🧠 Five-Tier Memory Architecture — NamoNexus

## 🚀 1. The 5-Tier Memory Strategy

NamoNexus bypasses the limitation of standard LLM contexts by utilizing a sophisticated **5-Tier Memory Architecture**. This system ensures that all generated knowledge, contradictions, and sessions are persistent, searchable, and structured.

```
┌────────────────────────────────────────────────────────┐
│               5-Tier Memory Stack                      │
├────────────────────────────────────────────────────────┤
│ 1. Vector Memory (Qdrant) — semantic continuity        │
│ 2. Graph Memory (Neo4j) — contradiction & lineage      │
│ 3. Persistent DB (PostgreSQL) — relational schemas     │
│ 4. Cache & Streams (Redis) — session state & queues    │
│ 5. Cross-Session Memory (ResearchMemory) — coordination│
└────────────────────────────────────────────────────────┘
```

## 🛠️ 2. Memory Tier Details

### 2.1. Vector Memory (Qdrant) — `src/memory/qdrant_connector.py`
* **Role:** High-speed semantic similarity searches.
* **Configuration:** Stores dense vectors generated by `EmbeddingProvider` (Sentence-Transformers).
* **RAG Precision Strategy:** We strictly enforce the **"Short Chunk Strategy"** for highly technical or precise texts (e.g. Abhidhamma and Dhamma datasets).
  * **Short Chunk Strategy:** Text is chunked in micro-paragraphs (100–150 tokens max) with overlap (20 tokens), prioritizing exact matching of technical terms over broad contextual paragraphs. This maximizes vector precision and prevents embedding "smearing."

### 2.2. Graph Memory (Neo4j) — `src/memory/neo4j_connector.py`
* **Role:** Linear tracking of hypothesis evolution and contradiction analysis.
* **Nodes:**
  * `Question`: Sub-questions created by planners.
  * `Hypothesis`: Statements proposed by agents.
  * `Critique`: Peer reviews.
  * `Contradiction`: Flagged logical conflicts.
* **Key Queries:** Tracing the parentage of a final synthesized conclusion down to its raw original sub-hypotheses.

### 2.3. Persistent DB (PostgreSQL via Alembic) — `src/memory/schema.py`
* **Role:** Structured master schemas and relational data persistence.
* **Core Tables:**
  1. `tenants`: Stores tenant containers, subscription tiers (`free`, `pro`, `enterprise`), domains, and status.
  2. `users`: Stores emails, password hashes, tenant associations, and user roles (`owner`, `admin`, `member`).
  3. `research_tasks`: Tracks long-running goals, status (`pending`, `completed`, `failed`), and output JSON payloads.
  4. `workflow_records`: Tracks active research workflows and sub-question splits.
  5. `hypothesis_records`: Immutable log of every proposed statement, confidence scores, and generation levels.
  6. `reasoning_traces`: Tracks reasoning lineage and duration per step.

### 2.4. Cache & State Store (Redis) — `src/memory/redis_runtime_store.py`
* **Role:** Transient data caching, session states, and message brokers.
* **Key Tasks:**
  * **Cognitive Sessions:** `CognitiveSessionManager` stores session parameters with a 24h TTL.
  * **Event Bus:** Backs `RedisEventBus` with stream messages.
  * **API Rate Limiting:** Stores sliding window request counts per API Key/IP.

### 2.5. Cross-Session Memory Orchestration (`ResearchMemory`)
* Combined container class: orchestrates retrieval across in-memory buffers, searches vector memories in Qdrant, and syncs finalized records to PostgreSQL via the `MemoryAgent`.

## 🗄️ 3. Relational Schema Blueprint (DDL Reference)

```sql
-- Core Tenants table
CREATE TABLE tenants (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name VARCHAR(255) NOT NULL,
    domain VARCHAR(255) UNIQUE,
    slug VARCHAR(100) UNIQUE,
    tier VARCHAR(50) DEFAULT 'free' NOT NULL,
    status VARCHAR(20) DEFAULT 'active' NOT NULL,
    is_active BOOLEAN DEFAULT TRUE NOT NULL,
    db_connection_string TEXT,
    encrypted_settings JSONB,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW() NOT NULL,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW() NOT NULL
);

-- Core Users table
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID REFERENCES tenants(id),
    email VARCHAR(255) NOT NULL INDEX,
    password_hash VARCHAR(255),
    role VARCHAR(50) DEFAULT 'member' NOT NULL,
    is_active BOOLEAN DEFAULT TRUE NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW() NOT NULL,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW() NOT NULL
);

-- Hypothesis Records (Persistent Cross-Session Knowledge)
CREATE TABLE hypothesis_records (
    id VARCHAR(36) PRIMARY KEY,
    tenant_id UUID REFERENCES tenants(id) NOT NULL,
    statement TEXT NOT NULL,
    confidence FLOAT DEFAULT 0.0 NOT NULL,
    topic TEXT NOT NULL,
    source VARCHAR(50) NOT NULL,
    session_id VARCHAR(36) DEFAULT '' NOT NULL,
    evidence JSONB,
    generation INTEGER DEFAULT 0 NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW() NOT NULL
);
```

## 🔄 4. Multi-Tenant Data Isolation (RLS Policies)

PostgreSQL Row-Level Security is actively enabled for all tenant-scoped tables:
```sql
ALTER TABLE hypothesis_records ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation_policy ON hypothesis_records
    USING (tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid);
```
This forces PostgreSQL to isolate all database accesses. Even a bug in the application routing layer cannot leak data across tenants, fulfilling NRE v5.0.0's security guidelines.
